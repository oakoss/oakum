# Changelog

## 0.8.2 (2026-10-31)

### Fixed

oakum 0.8.1 was tagged, but its binaries, crates.io crate, npm package and Homebrew formula were never published: a scheduled brownout of GitHub's retiring macOS 14 runners cancelled its Apple Silicon build. This release builds that target on macOS 15 and publishes the same changes.

## 0.8.1 (2026-10-31)

### Fixed

`oakum ci pr-status` and `oakum ci post-comment` treat a pull request comment as theirs only when a bot wrote it and its body starts with oakum's marker. A bot comment that merely quoted the marker could be overwritten or deleted. When updating the plan, they now update or create it before removing older copies, so a removal that fails leaves the current plan up, and the message says the plan was posted and which removal failed rather than that nothing was posted.

## 0.8.0 (2026-10-31)

### Added

`oakum ci post-comment DIR` posts the comment `ci pr-status --emit-comment DIR` wrote, from a job that holds the write token and has no checkout. It updates oakum's plan comment, or removes it when the emitting run had none, under the same ownership rule `pr-status` uses. The pull request comes from that job's own event (`pull_request`, or a same-repository `workflow_run`), never from the artifact. The body must start with oakum's marker, end with the closing line `--emit-comment` writes, and fit GitHub's 65,536-character limit; one that does not start with the marker or is over the limit is refused (exit 1).

`--emit-comment` now always leaves exactly one file, written whole: `oakum-pr-comment.md`, or `oakum-pr-comment.none` when the run has no comment. A run that stops first leaves neither. `post-comment` refuses as unverified (exit 2) when the artifact cannot be trusted whole (neither file or both, a body cut short, an entry that is not a regular file) or the token cannot write, so a lost artifact never reads as nothing to post and an earlier run's comment is never reposted.

With commits-only intent, each commit's summary now reaches only the changelogs of the packages that commit names. Before, every package releasing from a range listed every commit in the range, prefixed with the package it belonged to, so `alpha`'s changelog carried `- beta: ...` lines. Each commit now lands in its own section by its own level: a `fix` under `### Fixed`, a `feat` under `### Added`, where before all of a package's commits shared the section of its highest level.

A changelog template's `file` field for a commit-derived change now holds the commit's hash, where it read `commits`.

A Cargo crate and an npm package with the same name in one directory now both release from an unscoped commit that touches it, as coverage already counted. Before, commits-only planning refused with "commit-derived package `<name>` matches more than one workspace package".

`oakum migrate` from knope names each package's `scopes` list among the remaining steps, saying it was not carried over and that oakum attributes a commit whose scope names no package by the files it changes. The lists used to be dropped without a word.

`oakum ci pr-status --emit-comment DIR` with `pr-status = "none"` no longer refuses. It writes no comment or job summary, leaves the `oakum-pr-comment.none` marker in `DIR`, and exits 0 without calling GitHub, so the trusted job posting the emitted comment removes the old one after switching to `none`.

With conventional commits, a commit that asks for a release (`feat`, `fix` or breaking) and changes no package's files, under a scope that names no workspace package such as `fix(gamma)` or `fix(alpha,beta)`, is now reported instead of dropped without a word. A merge under such a scope is reported too, since its paths are not read. A commit with no scope, or a non-conventional message, is not reported. `status` and `ci pr-status` list it under "Released by a commit but reaching no package", `status --json` and the title and commit-message templates carry it as `unresolved_scopes` (`commit`, `scope`), and `check`, `version` and `generate` name it on stderr. Exit codes do not change, `--strict` included. A commit that releases nothing is not reported, and its ambiguous scope (a Cargo crate and an npm package sharing the name) now falls back to its paths instead of refusing the run.

`oakum status` and the `ci pr-status` job summary say what to do next. An empty plan with no bump file pending says so and names `oakum add`, and `oakum generate` when conventional commits are on. An uncovered package is followed by the command that covers it, `oakum add --packages <package>:<level>`, plus `oakum generate --from <base>` where `check` would offer it (or a conventional commit naming it, in a commits-only repository), and the pull request comment carries the same line.

The version pull request body from `oakum ci version-pr` now quotes each package's changelog entry under **Release notes**, one collapsible block per package, so a reader on the Conversation tab or in email sees what ships, not only what bumps. The entry is read back from the changelog the branch writes. An entry that would take the body past GitHub's 65,536-character limit, or that holds raw HTML which could break the page, is named with its `CHANGELOG.md` path instead of being cut, and a body still over the limit stops the run before anything is pushed.

### Changed

Running `oakum` with no command prints its help on stderr and exits 2, the usage-error code, where it printed `oakum` and exited 0. The help lists commands in the order a new user meets them (`init`, `add`, `generate`, `status`, `check`, then `version`, `release` and `ci`) and ends with the typical flow and a link to the guides.

`check --strict` coverage counts only a branch's own intent. A bump file already pending on the base branch no longer covers a pull request that changes the package it names; the branch needs its own bump file (`oakum add`), or an edit to the pending one. Under conventional commits only, only the branch's commits cover it, not unreleased commits on the base branch. `status`, `status --json` (`uncovered`) and the `ci pr-status` comment report coverage the same way. A base sharing no history with `HEAD` leaves coverage unverified (exit 2).

A package's `CHANGELOG.md` that is a symlink whose target does not exist no longer reads as absent. `check` reports it under "changelog(s) `oakum version` would refuse to append to" (exit 2), naming the link and the fix, and `migrate` lists it among the remaining steps; `version` already refused to write through it.

A manifest version set by hand above its highest tag, with no changelog section for that version, is now treated like an untagged hand-set version: `version` and `ci version-pr` refuse to bump past it (exit 1), and `check` names it as set by hand with the tag to cut, instead of stacking the next release on it. A version above its tag that has its section, as `version` writes, is still stacked on. A `0.0.0` or `0.1.0` manifest is checked against tags only when its changelog has a section for an older version, so a new package versions as before, while one whose changelog has one now needs full history: in a shallow clone `version` exits 2 rather than bump unchecked.

Help text states the `--from` default from one source: the merge-base with `origin/main`, else `main`, else `master`, with commit-derived intent starting at the highest reachable tag of each package oakum tags. `version` and `ci version-pr` say they read `--from` only for commit-derived intent. Options no longer cite ADR numbers, `check --strict` names both looks it gates (coverage and notes), and `version` describes itself in one line.

A manifest below its highest tag, such as 0.1.0 after `v0.2.0` shipped, no longer plans a version already released or below one. `check` fails naming both versions and the fix ("N package(s) below their highest tag"), `version` and `ci version-pr` refuse before any write (exit 1), and `status`, `status --json` (`hand_set`) and the `ci pr-status` comment show the plan as blocked. To tell, these read tags whenever the plan bumps a package oakum tags, tagged yet or not, so in a shallow clone they now exit 2 (`unverified`) and ask for full history; a fresh `0.0.0` or `0.1.0` package with no earlier changelog section still versions there.

`oakum migrate` from knope compares plans when nothing is pending. knope's dry run prints nothing and exits 0 then, which migrate read as the tool being unavailable, ending unverified (exit 2) on the usual time to migrate, right after a release. When the workflow it ran has a `PrepareRelease` step (or `knope.toml` declares none, so knope's own defaults run), that silence is now an empty before-plan: nothing pending on either side is reported as such and exits 0, and a bump file oakum plans that knope does not is a finding (exit 1). Silence from a workflow with no `PrepareRelease` step, which knope gives whether or not anything is pending, stays unverified and says why, as does output oakum does not recognise.

`check`'s staging look now sweeps the directory of every file `version` writes, including a nested workspace's `Cargo.toml`, `Cargo.lock`, `pnpm-lock.yaml` and catalog when they are regular files. A stray `oakum` staging file beside one of them (`rust/.Cargo.lock.oakum-write.…`) is reported as unverified (exit 2) instead of passing.

With conventional commits and change files off, the plan (`status`, `version`, `check`, `ci pr-status`, `ci version-pr`) now reads each package's commits since its own highest reachable tag, instead of `merge-base(origin/main, HEAD)..HEAD`. On the default branch that range was empty, so a commits-only repository planned nothing there unless every run passed `--from`; `version` now releases on `main`. A package never tagged reads all of its history. A package `version` released and no tag records yet (its manifest is above its tag and its changelog has the section) reads no commits until `oakum release` tags it, so the version pull request job running beside `release` does not plan the same release twice, wherever the release was cut; `check --strict` still reads the branch's commits for it, so a branch's own fix covers its change. `status` lists it under "Released, awaiting its tag", and `status --json` and the templates as `awaiting_tag`. A package oakum does not tag keeps the merge-base range. A shallow clone, a `--no-tags` remote, tags oakum cannot attribute, or one version tagged on two commits now make these commands unverified (exit 2) in commits-only mode, where the plan read no tags before. With a tag to read from, `status` no longer needs `git merge-base` for the plan, so a merge-base it cannot get now leaves only its coverage look unchecked (exit 0, "Coverage was not checked") rather than failing the run. `--from` still reads one range for every package, `generate` keeps the merge-base range, and `check --strict` still asks what changed since the merge-base, now against intent pending since each tag.

Conventional commits now release only for `feat` (minor), `fix` (patch) and a breaking change (`!` or a `BREAKING CHANGE` footer, any type: major), as knope and release-please read the convention. Every other type (`docs`, `chore`, `ci`, `refactor`, `test`, …) planned a patch and now releases nothing: it covers the packages it names, as a `name: none` bump file does, so `check --strict` does not report them as changed with no covering intent.

This applies to commits-only intent (`status`, `check`, `version`) and to `generate`, which writes a `name: none` entry for a package only such commits touched, and leaves their summaries out of a note that releases something. A non-releasing commit to a package the config does not version is not reported as "named by a commit but not version-managed". A message that is not conventional still releases a patch for the packages its files touch.

In a `CHANGELOG.md` that more than one managed package writes, such as a crate and an npm package in one directory, only a `## <name>@<version>` heading is a package's section, and `version` writes that heading there. A bare `## 0.3.0` no longer makes a hand-set sibling at 0.3.0 read as released by `version`, and each release body is its own entry rather than the first match. A bare heading for a package's version in a shared changelog, as earlier releases wrote, now stops `version`, commits-only planning and `release` (exit 1) with the heading to write, and `check` reports the version as set by hand. A template whose heading would read as any package's is refused there.

A version heading inside an HTML comment or a `<details>` block no longer counts as a section, and a bump-file note or template entry that leaves either open is refused like an open code fence. A changelog that leaves one open, which hides every heading after it, is named with its line by `check`, and `version`, commits-only planning and `release` refuse it (exit 1) until it is closed.

`status`, `status --json` and the `ci pr-status` comment now show when the plan bumps a version set by hand, which `version` refuses until it is tagged. The render names it under "Blocked by a version set by hand" with the fix `version` prints, and the PR comment lists it before the packages that would release. `status --json` and the templates carry it as `hand_set`, one entry per package with `name`, `ecosystem`, `version` and `fix`. `status` still exits 0 on a block. When it cannot read the tags or a planned package's changelog it needs to tell, such as in a shallow clone, it now exits 2 (`unverified`) rather than show the plan as unblocked, naming any version set by hand it did find; a plan with no version that could have been set by hand reads no tags, as before.

`oakum ci version-pr` exits 0 and writes nothing when a newer push has moved the default branch past the run's checkout: GitHub's compare shows the branch tip descending from `HEAD`, and stdout names both commits. Back-to-back merges no longer leave a failed version-pr job behind the run that rebuilt the pull request. A tip that is behind or has diverged from `HEAD`, or a compare GitHub answers with 404, still exits 1, now naming which; a compare that could not be read exits 2.

`oakum release` tags the commit that set each package's pending version, not `HEAD`: it walks back along `HEAD`'s first parents to where the manifest (or, for `version.workspace = true`, `[workspace.package]`) began declaring the version. A commit that lands between the version commit and a delayed `release` now stays after the tag and is planned in the next release, rather than shipping inside a tag no plan covered. A version a merge brought in is tagged at the merge, and a package created at its version is tagged where its manifest appeared.

`release` now refuses as unverified (exit 2) where it used to tag `HEAD`: when the walk reaches a manifest that names no version oakum can read before it finds where the version was set, when the newest commit to change the manifest declares another version, or when the commit that set the version lacks the changelog section `HEAD` has for it, as when a version was bumped by hand before adopting oakum. Tag the release by hand and run `release` again to publish it. A working tree holding changes is refused before the walk. The skip-ci refusal now says that a later commit does not move the tag: tag a clean commit by hand, or start the downstream workflow by hand.

The release body follows a symlinked changelog in the tagged commit rather than falling back to the title, and a `+build` release takes its body from a bare `## <version>` heading, as `check` already matches it. A link git will not follow (one that loops, is absolute, or leaves the repository) still falls back to the title, and the notice now names which.

`oakum ci version-pr` no longer opens a version pull request whose only change is deleting bump files that release nothing, such as a `none`-only bump file from a tests-only change. It prints `nothing to version`, naming how many pending bump files release nothing, and leaves them for the next real release to consume. A version pull request an earlier plan opened is still refreshed to match, so it stops offering a release whose intent left the default branch; a plan that also bumps a package opens the pull request as before.

### Fixed

In a repository using git's reftable ref format, git loads the ref store whole: one table or `tables.list` it cannot read, in the shared store or a linked worktree's own, makes git list no tags at exit 0. Every command that reads tags now checks each table first, read by path as git reads it, and reports one that cannot be opened, is not a regular file, or does not start like a reftable table as unverified (exit 2), naming the file. Before, the run stayed unverified only because `git refs verify` crashed on that store, and the message told you to run that same crashing command.

## 0.7.0 (2026-10-26)

### Changed

A git listing that skipped part of what it was asked for is unverified (exit 2) instead of read as complete. Three cases that exited 0 before:

- A tag listing beside `warning: ignoring broken ref` (a tag ref holding garbage, or one git cannot read). git lists the other tags and exits 0, so the missing tag could be the last release.
- A worktree listing beside git's bare `<path>: <system error>` line, such as `beta/src/lib.rs: Permission denied`. `git status` drops a file it cannot `lstat` that way, so a changed package went unseen. Other unprefixed stderr, such as a clean filter's own output, still leaves the listing standing.
- A tag listing that `git refs verify` says could not open a directory under the repository's `refs/tags`, wherever its git directory lives: beside the worktree, inside a submodule's parent, or a separate git dir. git drops the tags in that directory without a word, and an empty listing read as never released. oakum now runs `git refs verify` after every tag listing. A git directory kept under a folder path holding `refs/tags` can't be told apart, so there an unopened directory in another namespace is unverified too. Its warnings about a ref's form, such as a missing newline or a symlink, change nothing. On a git older than 2.47, which has no `refs verify`, the listing stands as before.

A clone whose remote fetches only some branches (`git clone --single-branch`) is unverified (exit 2) where oakum reads every tag (`release`'s check of local tags and `migrate`'s tag-format derivation), instead of read as a complete tag set. git follows only the tags on the branches it fetches, so a release tagged on another branch was missing and the short set read as the whole. Readers of the tags on HEAD's history (`check`, `version`, `reachable-tags`) are unaffected: the fetched branch brought every tag on it.

oakum judges the remote it reads tags from (`origin`, else the first by name). It reports when no fetch refspec stores every branch, a negative refspec takes some branches back, or the remote has no refspec at all, unless `tagOpt` is `--tags` or a refspec stores every tag under `refs/tags/`. The message names the refspec and the fix: `git config --replace-all remote.<name>.tagOpt --tags`, then `git fetch --tags -- <name>`. `actions/checkout` at `fetch-depth: 0` keeps the refspec for every branch and is unaffected.

The `--no-tags` check now follows what git fetches, too: a `tagOpt` value git does not recognise no longer hides an earlier `--no-tags`, a `git clone --mirror` (whose refspec stores every tag) is no longer reported as tag-suppressed, and a negative refspec that takes tags back counts against it. Remote settings are read with `git config -z`, so a remote whose name holds a space no longer breaks the read.

Known limits. Both checks read what the next fetch would bring, not what the last one did, so a remote widened (or set to `tagOpt --tags`) but not yet fetched reads as whole. In a single-branch clone, checking out a branch fetched by name into `FETCH_HEAD` alone leaves the tags on it unfetched, and the HEAD readers do not notice.

A bump-file note that keeps one section and loses another is now caught, as one that loses them all already was. A heading with nothing under it reaches no changelog, and when another heading in the same note rendered, the release looked complete while the empty section disappeared without a word. `add` refuses such a note before writing, and `check` reports it (refusing under `--strict`), each naming the empty heading: "has a heading with nothing under it (`### Fixed`)". A note that opens with a heading, an empty note, and a coverage-only note are unaffected.

`add` refuses, before writing, a bump file that releases a package the config does not version: one `include`/`exclude` leaves out, or a private package without `private-packages.version = true`. `status`, `check` and `version` all refused that file, so it could never release; the refusal now comes while the author is still there, naming the setting. A `name:none` entry is still written, since it releases nothing. `check` now accepts such an entry too: it refused one that `status` and `version` accepted.

With commits-only intent, a commit whose scope names a package the config keeps but cannot version is reported rather than dropped without a word. `status` prints "Named by a commit but not version-managed". `status --json`, the `commit-message` and `title` templates, and the version pull request's body carry it as `named_unmanaged`, and the `ci pr-status` comment lists it. `check`, `version` and `ci version-pr` print it on stderr without gating, `--strict` included, whether or not anything releases. A package already listed as changed but not version-managed is not repeated, and an excluded package stays silent.

## 0.6.4 (2026-10-24)

### Fixed

Two kinds of error message now say why. A GitHub request that fails names its cause, such as `operation timed out` or a refused connection, where it stopped at "error sending request for url". A file oakum reads or creates through a symlink it cannot use is named as one: a dangling link (as `version` meets on a dangling `CHANGELOG.md`) says the symlink's target does not exist instead of "File exists", and where cap-std reported "a path led outside of the filesystem", the message now says the file is reached through a path that leaves the repository, or through a symlink with an absolute target, neither of which oakum follows, or, for a link that is itself absolute, says just that. Exit codes are unchanged.

## 0.6.3 (2026-10-24)

### Fixed

When `version` fails creating a file and rolls back, a file it cannot check is named instead of being taken as never created. A stat that failed for any reason but the file being absent, before the create or after it, was read as nothing to clean up, so the failure report described a tree it had not checked. It now says it could not check whether the run created the file, and why, and to remove it only if the run did; the consume marker stays so the next `version` refuses rather than plan over it. A create refused because the file already exists names nothing, since it created nothing.

A YAML catalog pin that shares an anchor with another entry moves alone. `version` rewrote the anchored value, so a pin written as `*caret` also moved every other entry using `&caret`, including another package's, and the next `pnpm install` failed. Now an alias pin is written out as a quoted literal range and the anchor keeps its value; a pin that carries an anchor is rewritten and its aliases are written out, quoted, with the old value. An entry that reaches the pin through an alias of a whole table still moves with it. A line on stderr names each case once the files are written.

Recovery advice after a `version` that failed and rolled back is right in more cases. The consume marker is now marked as rolled back before the rollback's first step, so a run stopped partway through it is advised to keep none of its writes instead of being read as one whose writes landed. That advice points at `git status` and `git diff` rather than the failed run's own message, which may be gone, and says to keep edits made before the run. A marker that could not be marked says why, a marker overwritten in place keeps none of its old listing, and an empty marker beside a set-aside bump file is no longer read as a consume that landed, whose advice would remove bump files never applied. The advice for set-aside bump files of unknown state says to remove one the kept writes already applied.

Files oakum rewrites keep their permissions. `version`, a rollback, `upgrade` and `migrate` replace a file by renaming a new copy over it, and that copy was created with default permissions, so an executable manifest came back `644` (a mode change in `git diff`). The new copy now takes the old file's permissions; on a filesystem that cannot keep them, the file is still written and a warning says so. A file's owner and inode still change.

A file `version` rewrites through a symlink stays a symlink. `version` read a symlinked manifest through the link but replaced the link with a regular file, so the shared file it named kept the old version. Writes now follow the link: the file it names gets the new text, staged beside that file, and the link stays, and `check` looks for staging files beside a link's file too. A link oakum does not follow safely (one into a `.git`, one it cannot resolve, one whose file refuses the new text, or one whose file another write of the same run also names) is replaced by a regular file as before, and stderr names the file that did not get the new text.

A git, `cargo metadata` or pnpm child, or a source tool `migrate` runs, that goes past `OAKUM_REMOTE_DEADLINE` is killed together with what it started and is still waiting on, such as a signing program, a credential helper or an ssh `ProxyCommand`. The message names those programs: on stderr, and in `migrate`'s report on stdout. Before, only the child was killed and the rest kept running. The tree is stopped before it is killed, so nothing it starts in the meantime escapes. A process whose parent had already exited is not reached. When oakum cannot vouch for the whole tree, the message says what the child started may still be running. That happens when oakum could not list the tree or kill a process in it, a process would not stop or exited before it could be stopped, the child kept starting processes faster than oakum could stop them, or a process could not be confirmed as still under the child and was let go rather than killed. A passphrase prompt that gpg's agent shows through pinentry belongs to the agent, not to git, so the agent decides when it closes.

`version` and `ci version-pr` name the lockfile entries left for `pnpm install` once the files are written, so a run refused after planning no longer lists entries it never wrote. The version pull request also lists catalog entries that share a YAML anchor with a bumped pin.

`check` and `status` no longer count a version commit's own writes as an uncovered change. A range holding the commit that ran `version` reported its packages as changed with no covering intent, and the suggested fix would have bumped them a second time. A commit that deletes a bump file now has its manifest, changelog, lockfile and catalog edits left out of coverage in each package directory whose `CHANGELOG.md` it also wrote, whatever its subject says. Its other edits, a merge's, and a later commit's still count.

## 0.6.2 (2026-10-23)

### Fixed

`version` finishes a pre-release instead of skipping past it. A patch bump on `2.0.0-rc.1` now gives `2.0.0` rather than `2.0.1`; a minor bump on `2.1.0-rc.1` gives `2.1.0`, and a major bump on `2.0.0-rc.1` gives `2.0.0`. A bump that leaves the line the pre-release was heading toward still moves past it: a minor bump on `2.1.3-rc.1` gives `2.2.0`. This matches node-semver's `inc`, which changesets uses. Under the default `versioning = "zero-major"`, a major below 1.0.0 is still read as a minor first, so a major bump on `0.3.0-rc.1` gives `0.3.0`; under `versioning = "semver"` it gives `1.0.0`.

Discovery no longer writes `pnpm-lock.yaml` into a lock-free pnpm workspace that declares its package manager. pnpm 11 wrote one despite `--config.lockfile=false` under a `devEngines.packageManager` naming a version it accepted, and under a `packageManager` naming a newer pnpm; pnpm 12 did when a `devEngines.packageManager` switched it to an 11. Discovery now has the pnpm on `PATH` answer, so a declaration pnpm would refuse, such as a `devEngines.packageManager` array or `onFail: "error"` naming another pnpm, no longer stops discovery.

The workflow `init` and `migrate` print now takes the pnpm version from a `devEngines.packageManager` array that names an exact one, since `pnpm/action-setup` reads only the object form, instead of asking pnpm. An array naming a pnpm other than the one on `PATH` gets that pnpm as the workflow's `version` input rather than exiting `unverified`. An array whose version is not an exact one, such as a range, still asks pnpm, which under pnpm 11 can write a lockfile when the version matches it.

In a pnpm workspace, a dependency whose range the same-named member's current version does not satisfy, such as `"is-number": "7.0.0"` beside a workspace member `is-number` at `1.0.0`, is no longer read as depending on that member. pnpm installs it from the registry, yet `version` rewrote it to the member's new version on a release that left the range. This covers plain ranges, `npm:` aliases and `catalog:` entries; a `workspace:` dependency still always counts as depending on the member.

`oakum ci pr-status --emit-comment <dir>` no longer writes the comment file when `pr-status = "summary"`. It wrote `oakum-pr-comment.md` anyway, so a trusted job that posts whatever it finds there posted a comment the config had turned off. It now writes the job summary as configured, removes a comment file left by an earlier run, says on stderr that `summary` turned the comment off, and exits 0.

The `leftover tag ambiguity` refusal from `check`, `version` and `release` now says how to resolve it, on a line after the tags it names:

- Two versions of one package tagged on one commit: keep the tag for the version that commit's manifest names and delete the other, on the remote too if it was pushed.
- A bare `v<version>` tag with several packages tagged: use `<package>/v<version>`.
- A version-like tag in a shape oakum does not read: rename it to one it does.
- A tag naming a package the workspace no longer has, as after a rename: delete it, or tag the release with a current package's name.
- A tag whose package name exists in two ecosystems: rename the package it did not release.

The refusal and its exit code are unchanged, and so is the `summary` of its `check --json` refusal, which keeps the first line only.

## 0.6.1 (2026-10-23)

### Fixed

Errors, warnings, prompts, and the summaries `oakum status` and `oakum version` print now escape bytes that could rewrite the terminal, such as an escape sequence or a bidi override in a bump file's name or a pnpm package name. So does the plan `oakum ci pr-status` prints to stdout when `GITHUB_STEP_SUMMARY` is unset; the job summary file keeps the text as rendered. Before, only some messages did: `oakum status` printed a bump file's name raw when refusing it, and the summaries printed such names raw. Error text quoted from pnpm, cargo, git or the old release tool prints without its colour codes. Combining accents print as written rather than as `\u{301}`. Output meant for scripts is unchanged: `--json`, and the paths, URLs and tags that commands print as their result.

`oakum migrate` runs bumpy, changesets and knope under `OAKUM_REMOTE_DEADLINE` like every other child: one whose answer has not arrived by then is named, and `migrate` exits `2` (unverified) instead of hanging.

`migrate` also finds those tools on `PATH` the way discovery finds pnpm, including a Git Bash `PATH` on Windows (`/c/Users/...`, or `:`-separated entries), which its lookup used to miss.

Both lookups now share one reading of `PATH`. On Windows, a quoted entry such as `"C:\Program Files\knope"` and a verbatim one such as `\\?\C:\tools` are each one directory, and only a name with a `PATHEXT` extension is taken, never an extensionless file. Elsewhere, `PATH` is read as the shell reads it, so `/a/bin` is a directory rather than drive `A:` and a bare `pnpm` wins over a `pnpm.EXE` beside it. On every system an empty `PATH` entry is skipped rather than read as the current directory, so it no longer runs a `pnpm`, `bumpy`, `changeset` or `knope` file from the repository being inspected.

Four messages now say what to do:

- A version no tag records (`never released, but the manifest is 1.0.0`) names the tag to cut, rendered from `tag-format` or the default: `` `git tag @demo/a/v1.0.0 <commit>` ``. A `tag-format` whose tag oakum could not read back as that version names none.
- In `oakum check`, a change with no covering intent names `oakum add --packages <package>:<level>`, and, when conventional commits are on, `oakum generate --from <base>` over the range `check` read.
- `oakum add` without `--message` says the bump file's changelog entry will be empty.
- `oakum init` and `oakum migrate` say why they reach GitHub when the lookup for the printed workflow's action pins fails, and that nothing was written.

### Added

`check` now reports `.changeset/_schema.json` when its bytes differ from what the running oakum generates, or when it cannot be read, whatever `_config.toml`'s `#:schema` line says; a missing one is reported only when that line names it. The stale and missing notes name `oakum upgrade`, after settling the install pins when they disagree, cannot be read, or are not exact versions. The `check` scope line now lists `schema` among the looks.

### Changed

The workflow `oakum init` and `oakum migrate` print for a Cargo repository pins `taiki-e/install-action` to v2.87.30 (was v2.87.22).

oakum reads its version from the install pin, not `tool-version` (ADR-0038). `add`, `generate`, `version`, `ci version-pr`, `release`, `upgrade`, `init`, and `migrate` compare this binary to the version pinned in `.github/workflows`, a composite action under `.github/actions`, `package.json`, `.mise.toml` or `mise.toml`, or a Cargo workspace member named `oakum`, and refuse with exit 1 when they differ, naming the fix for that direction. `add`, `generate`, `version`, and `ci version-pr` refuse with exit 2 when nothing pins oakum, when pins disagree, or when a pin cannot be read or is a range such as `^0.5.0`; a repository that relied on `tool-version` alone with a global or Homebrew install now needs a pin: `pnpm add -D --allow-build=@oakoss/oakum @oakoss/oakum@<version>`, or `"github:oakoss/oakum" = "<version>"` under `[tools]` in `.mise.toml`. A symlink to a missing target where a pin source would be is unverified, as a pin that cannot be read is, not read as no pin; `check` included. `upgrade` refuses with exit 2 when pins disagree or cannot be read; when nothing pins oakum it continues and says so on stderr. `release` leaves a missing or unsettled pin to its install-pin precondition, as before. `init` and `migrate` check the pin on every run, a fresh repository included, and write their files whatever the pin says unless it names another version: with no pin they print the pin as the next step and exit 0, pointing at the printed workflow's install line when it has one, and when pins disagree or cannot be read they print that and exit 2 after writing. `check` passes pins that agree with each other whatever `tool-version` says, and reads `github:oakoss/oakum` as a pin. A Cargo workspace member named `oakum` is found wherever Cargo finds it, member globs of any shape and a path dependency Cargo makes a member included, so a repository that got exit 2 for an unsupported `workspace.members` glob now passes, or gets exit 1 when its pin really differs; the member is read from the repository root with `cargo metadata`, so a Cargo workspace it cannot read (no `cargo` on `PATH`, a listed member missing) is an unread pin source, exit 2 unless other pins name another version. `init` and `migrate` no longer write `tool-version` into the `_config.toml` they create, and `version` no longer rewrites it when it bumps a Cargo workspace member named `oakum`. `_config.toml` may omit `tool-version`, and any value in it parses, a range included: nothing reads it, and the schema no longer requires it. `upgrade` removes `tool-version` from `_config.toml` in whatever shape it takes, keeping comments, including a `#:schema` line above it, and the rest of the file; it no longer writes or reports a version, and its message when nothing changed no longer names one. While the key is present, every command that loads the config except `upgrade` prints one stderr line saying oakum no longer reads it and naming `oakum upgrade`; exit codes and stdout are unchanged. The version-PR body and changelog footer stamp this binary's version.

oakum reads npm ranges with js-semver 1.0. A dependency range with `==` before a full version, such as `==1.0.0`, is now refused, as pnpm and node-semver refuse it; oakum read it as `1.0.0` before. `==` before a partial version, such as `==1`, still reads as before. The refusal for an unreadable range names what is wrong, such as `unexpected character '=' while parsing major version`, instead of `invalid number`.

Templates render with minijinja 3, which follows Jinja2 more closely, so a template you write can render differently or fail where it rendered before. The main differences: a printed list or map uses single quotes (`['a', 'b']`), and `zip` and `items` give tuples that print as `(1, 3)`; `round` rounds half to even (`2.5` gives `2.0`); `title` leaves the letter after an apostrophe lowercase (`Don't`); `max` and `min` compare strings ignoring case; a boolean passes `is number`; unary minus binds as in Jinja2 (`-a.b` negates `a.b`); dividing by zero and `format` with an undefined value fail the render instead of printing `inf` or nothing. An undefined variable's error names the expression, such as `` `name` is undefined ``, before oakum's list of what the template receives. Built-in templates render the same. minijinja's [3.0.0 release notes](https://github.com/mitsuhiko/minijinja/releases/tag/3.0.0) list every change.

Building oakum from source needs Rust 1.99.1 (was 1.98.1).

### Fixed

Discovery's `cargo metadata`, `pnpm root -w` and `pnpm list`, and the `pnpm --version` that `init` and `migrate` run, now run under the same wall-clock deadline as oakum's git children: five minutes, or `OAKUM_REMOTE_DEADLINE` seconds, per child. `release` re-checks a `git tag` or `git push` that never answered. When the tag is found locally, or the push on the remote, it stops with exit 1 and names the stage (`tagged` or `pushed`); when the tag is not there, the stage is the one before. Only when the re-check fails too is the stop unverified (exit 2). A `git tag` that never answered no longer reports `completed: none` over a tag it wrote. The detail under an unverified stop says `unverified` once, not twice.

A `git` that cannot be started, or that answered with a failure, keeps its exit.

## 0.5.0 (2026-10-05)

### Changed

`oakum version` no longer loses bump files when it is killed or fails while consuming them. It used to delete each consumed bump file and hold the only copy in memory, so a signal, an OOM kill or a cancelled CI job in that window removed files with nothing on stderr, and a later failure could leave some unrestorable. Consumed files are now moved aside to `.<name>.oakum-consume.*` names and removed only after every write has landed, and a failure moves them back. While it writes and consumes, `version` also holds a `.version.oakum-consume.*` marker in `.changeset/`. A run killed partway leaves these files behind. The next `check` names them and exits 2, where it used to pass. The next `version` and `ci version-pr` refuse (exit 1) rather than apply the bump files left beside them a second time. The refusal says whether the writes landed and how to recover. If a set-aside file cannot be moved back, `version` names it and the move that restores it. If every write landed but a set-aside file cannot be removed, `version` prints what it wrote, then names the file and why, and exits 1.

`oakum release` now tags the first version `oakum version` writes, whether `0.1.0` or `0.0.x`. An untagged package was owed a tag only above `0.1.0`, so the `0.1.0` or `0.0.1` that `oakum version` writes from `0.0.0` read as an untouched starting version: `check` passed and `release` printed `nothing to release`. Now, with no reachable tag, only a manifest at `0.0.0` or `0.1.0` whose `CHANGELOG.md` has no section for that version is a starting version. Every other untagged version is owed a tag: `release` cuts it, and `check` refuses (exit 1) until it does. That includes a hand-set `0.0.5`, which `check` used to pass. A version with a changelog section is named as waiting for `oakum release`; one without still says to tag the version you meant. To release a `cargo init` crate at `0.1.0` as-is, add a `## 0.1.0` section to its changelog. When an untagged `0.0.0` or `0.1.0` has a changelog oakum cannot read, a dangling symlink included, the tags look reports it `unverified` (exit 2) and `release` refuses rather than skipping it; the other packages' findings still print. Above those versions an unreadable changelog only changes the wording.

`oakum version` no longer bumps past a version someone set by hand. When the plan would bump a package, cascades included, whose manifest version has no tag and no changelog section, such as a `0.1.1` or `0.0.5` someone typed, `version` and `ci version-pr` exit 1 before writing anything and name every such package. The fix is to tag the version you meant, or to run `git fetch --tags` if its tag exists on a remote; `check` now gives that second option too. A hand-set version the plan leaves alone does not stop the run; `check` still reports it. A placeholder `0.0.0` or `0.1.0` is still bumped from, and an untagged version that has its changelog section (one `version` wrote and `release` has not tagged yet) is still stacked on. When the changelog or the tags cannot be read for such a package, `version` exits 2 rather than guess, so a shallow or no-tags clone now stops it whenever a package it bumps has no changelog section for its current version.

`oakum add`, `generate` and `plan-intent` now refuse an `include` or `exclude` entry that names no package in the workspace, as `status`, `check`, `version` and `release` already did. They used to accept it, so `add` and `generate` wrote a bump file that every later step then rejected. The refusal, from every command, now names `.changeset/_config.toml` and lists the workspace packages to choose from (the first 20).

Commits now count only toward packages the config versions, both in `generate` and when commits are the plan's intent: a package `include`/`exclude` leaves out, or a private package without `private-packages.version = true`, is skipped. A commit touching only such a package no longer makes `version` refuse in commits-only mode, and `generate` writes no bump file for it, naming the packages it skipped and the setting to change; a commit touching several packages names only the versioned ones.

A changelog `template` must now render a heading oakum can read back. `check` and `release` find a version by its changelog heading, and a template that wrote, for example, `## demo@0.1.0` left the first `0.1.0` looking like an untouched placeholder, so `release` never tagged it. Headings of the form `## <name>@<version>` are now read for the package they name, alongside `## <version>`, `## [<version>]` and `## v<version>`. `version` exits 1 before writing anything when the template renders any other heading, such as `### {{ version }}` or `## Version {{ version }}`, and names the shapes that work. It also exits 1 when the template renders nothing for a bumped version, such as a cascade whose template writes only when there are notes; that version would otherwise have no section. Whatever the template, `version` exits 1 when a new entry leaves a code fence open, for example a bump file note that ends inside one, or when a fence the existing changelog leaves open would hide a new heading; either would hide headings from `check` and `release`.

### Fixed

The workflow `oakum init` and `oakum migrate` print for a Cargo repository now installs oakum with `taiki-e/install-action` (`tool: oakum@<tool-version>`), pinned to a release oakum ships with. The step it replaces, `run: cargo binstall --no-confirm oakum@<tool-version>`, cannot run on `ubuntu-latest`, which does not ship `cargo-binstall`. For the same reason `migrate` no longer tells a Cargo repository without a pin to add `cargo binstall` to it; the printed workflow is the pin it offers. `check`'s refusal for a repository with no pin names the install-action step as its example instead of `cargo binstall`. oakum is not in install-action's own tool list, so the action installs `cargo-binstall` and uses it; `cargo-binstall` 1.24.0 resolves `oakum@0.4.0` for `x86_64-unknown-linux-gnu` from the GitHub release (dry run). `oakum check` reads the new step as the install pin, as it read the old one. npm workspaces are unchanged.

Oakum notices sooner that a git child has finished: the wait polled every 5 ms, so each child cost up to a poll's worth of idle time after git had already exited, and a command can run many of them. It now polls every 1 ms. Measured on macOS, `oakum check` in this repository dropped from 185 ms to 153 ms (fastest of 15 alternating runs). Output is unchanged.

`oakum check`, `oakum release` and the other commands that verify the install pin no longer hang when a pin file is a FIFO. The look opened `package.json`, `.mise.toml`, `mise.toml` and `.github/actions/*/action.yml` with a blocking open, so a FIFO nobody wrote to stalled the command forever. It now opens them non-blocking, as oakum's other file readers do, and refuses as `unverified` (exit 2), naming the file that is not a regular file. A missing file and a dangling symlink still read as no pin there. A `cargo` or `pnpm` reached through a mise shim reads `mise.toml` itself, so on such a PATH a FIFO there can still block before oakum looks.

When this binary is older than the repository's `tool-version`, the refusal no longer tells you to run `oakum upgrade`. Following that advice rewrote `tool-version` down to the older binary and exited 0, so a contributor with a stale local install downgraded the repository by doing what the error said. The refusal now names the pinned version to install and says `upgrade` would downgrade the repository. A binary newer than the pin still names `oakum upgrade`. Stderr only; the exit code is unchanged.

An exported `GIT_LITERAL_PATHSPECS`, `GIT_GLOB_PATHSPECS`, `GIT_NOGLOB_PATHSPECS` or `GIT_ICASE_PATHSPECS` no longer changes what oakum asks git. Oakum writes its pathspecs for git's defaults, and under `GIT_LITERAL_PATHSPECS=1` the exclusions in `oakum migrate`'s gate look became literal file names: the look searched nothing, and a repository whose hook names `.bumpy/` was told no file names the old bump-file directory. Under `GIT_ICASE_PATHSPECS=1`, `oakum release` refused before tagging, because git rejects the `:(literal)` pathspec it reads the changelog through. Oakum now clears these variables for every git child it runs, as it already clears git's trace variables.

Under pnpm 12, discovery no longer writes `pnpm-lock.yaml` into a pnpm workspace, or rewrites the one it has. Every pnpm call oakum makes (`pnpm list`, `pnpm root -w`, and the `pnpm --version` that `oakum init` runs) created a lockfile, mode 0600, in a lock-free workspace that declares its package manager, so `oakum status`, and any other command that discovers packages, left an untracked file behind; under an array-form `devEngines.packageManager`, `init` also rewrote an existing lockfile. Oakum now passes `--config.lockfile=false` on each call. Measured on pnpm 8.15.9, 9.15.9, 10.34.5, 11.25.0, 12.5.1 and 12.6.0: each accepts the flag and prints the same output with it. pnpm 11 still writes one under a `devEngines.packageManager` declaration or a `packageManager` naming pnpm 12; the flag does not stop it there. Output and exit codes are unchanged.

## 0.4.0 (2026-09-21)

### Added

`oakum check --json` prints a versioned `CheckReport` instead of the prose report: every look the run could perform, what each established, and which refusal decided. A caller that must see both outcomes of a mixed run now has somewhere to read the second — ADR-0035 ranked a finding above a look that did not happen and named the cost: the unverified outcome survives only in the `also` prose. A look nobody asked for reports `not-asked`, and one that said something without refusing reports `reported`, so neither can read as a look that happened and found nothing. A look that raised several refusals carries every one of them with its own evidence, rather than the first alone. The document also carries what the run covered — the packages selected, the base it diffed from or why that could not be named, and whether coverage gated — which the prose report says on stdout and `--json` replaces. Refusals still reach stderr and the exit code is unchanged, so one run yields a document and a human-readable failure.

### Changed

A bump file whose note is a heading with nothing under it renders no changelog section, so `oakum version` consumed the file and the release said nothing about what its author wrote, with no warning anywhere. `oakum add` now refuses to write such a note, naming `--none` for a change that is deliberately releaseless. `oakum check` reports one always and refuses under `--strict`, the shape its coverage look already uses, so a repository green today stays green until it opts in. `version` itself still says nothing when it consumes one, so a repository that never runs `check` still loses the note at release time. Three shapes that render nothing on purpose are untouched: a coverage-only (`none`) entry, a bump file with no note, and a note that is only whitespace. A file that drops only one of several headings is not reported either. Breaking for a repository that has such a file and runs `check --strict`, or an `add` whose message is a bare heading; both exited 0 before and exit 1 now.

### Fixed

When `oakum version` fails partway and cannot restore a bump file it already deleted, the failure now names that file and prints the opening lines of what it held. The file is gone at this point, so a later run cannot see it: it consumes whatever is left and reports success at a version nobody asked for. Measured on a real run — a failed `version` destroyed a `minor` bump file, and the next run shipped `0.1.1` where `0.2.0` was intended, at exit 0. The message says a file git has a copy of, committed or staged, comes back with `git checkout`, and shows the text for one that was never committed. The excerpt is bounded by lines, by columns and by file count, and the entry list above it by file count, each saying what it elided. Everything user-supplied in this message — the cause, each path, each error and each excerpt line — is escaped, since a bump file and the path naming it can arrive from a pull request and this is the one path to a raw terminal; script joiners and combining text still render. Exit codes are unchanged; a delete oakum could not undo is a finding it measured, so it still exits 1 (ADR-0037).

The `check --json` scope field `gating_coverage` is now `gating`, and carries the names of the looks `--strict` decides rather than a yes or no. `--strict` gates two looks as of this release — coverage, and the notes look that refuses a bump file note reaching no changelog — so a consumer that could only ask about coverage could not tell which of them refused; the names match `looks[].look`, so the two can be joined. The field says what `--strict` decided, not what the looks then managed: a look that could not run is still named, and reports `unverified` in its own row. An empty list means `--strict` was not asked for. A `patch` rather than a renamed field under the breaking row, and no `schema_version` bump: `check --json` has not appeared in a release — it was added after the v0.3.2 tag and its note is still pending — so no consumer can be holding the old name (ADR-0016 on a field that has never shipped).

`oakum migrate` no longer reads a `git grep` that exited 0 without naming a file as a search that found nothing. Real git cannot answer that way — a match prints the path, and both no-match and an empty index exit 1 in silence (measured on git 2.55.0 and Apple Git 2.54.0) — so the shape only ever comes from a wrapper that failed to look, and the gate find it produced was a look nobody completed. Such a run now refuses as `unverified` and exits 2 where it printed that no file names the old bump-file directory and exited 0. No repository running real git changes behavior.

## 0.3.2 (2026-09-17)

### Fixed

The version pull request is titled `chore(release): version packages`, the same sentence as the version commit. Where a repository takes its squash subject from the pull request title (`squash_merge_commit_title = PR_TITLE`), the old default — `Version Packages` — landed on the default branch instead, and a conventional-commit gate reading there refused the one commit oakum generates; the conventional message it wrote never appeared. GitHub's own default, `COMMIT_OR_PR_TITLE`, takes the subject from the single commit, so a repository left at that setting never saw this, and neither did one merging or rebasing, where the version commit lands carrying its own message. The two defaults sat four lines apart in the same file and disagreed either way. Set `title` in `.changeset/_config.toml` to keep the old string; its schema description now says what it falls back to and that a configured `commit-message` does not move it.

`check` names a package that changed outside `HEAD` — staged, edited or untracked — instead of passing over it. The coverage look reads commits while intent is read from the working tree, so a change that is not yet a commit was in neither half, and `--strict` exited 0 on a tree it refuses one commit later. The scope report now names both ends of the diff (`<base>...HEAD`) rather than reading as a comparison against the tree in front of you.

What that look could not read is said too: a working tree `git status` cannot walk, or can walk only in part, is reported rather than passed over in silence. Both are advisory, like the rest of this half — they name what went unread without changing any exit outcome. `release` reports them on the same terms.

`ci pr-status` says why it posted nothing on each of its three non-posting paths: an empty plan, the version pull request, and `pr-status = "none"`. Only the fork and token failures announced themselves before, so an empty plan and a swallowed failure looked alike from the workflow's side. A leftover plan comment this run's token could not remove is named as well, rather than leaving a line about what was not written to imply nothing was left behind.

Every git child now runs under `LC_ALL=C`, so the diagnostics oakum quotes back to you are in one language whatever the surrounding locale.

`check` names a package whose coverage a pull request will not receive. Changed packages are read from commits while intent is read from the working tree, so a bump file that is not committed — or one that is committed and has since been edited to name another package — covered a change that was committed, and `--strict` exited 0 while the ref you were about to push exited 1, with nothing said. The mirror of the change named outside `HEAD`, which this release also carries: there the change is invisible, here the coverage is.

The question is asked of `HEAD` itself, reading the intent its tree carries rather than guessing from which files are staged. That is what catches the ordinary flow: commit a bump file, touch a second package later, add a line to the file you already have. It costs nothing where there is no intent on disk to rest on, and nothing at all under `conventional-commits`, where both halves already read commits.

Advisory, like the rest of that half: it names what a pull request will not get without changing any exit outcome. An uncommitted bump file is the normal state seconds after `oakum add`, so refusing would fire on nearly every local loop.

## 0.3.1 (2026-09-16)

### Changed

The workflow `init` and `migrate` print identifies the version pull request by head repository and author, not by branch name alone. `github.head_ref` carries no owner, so in a public repository any fork could name its head branch `oakum/version-packages` and skip `oakum check --strict`; a collaborator could do the same from a branch in the repository itself, and so could anyone pushing to the bot's branch, since that raises a `synchronize` whose pull-request author is still the bot. All four terms hold for any repository, so nothing has to be filled in: they test the head repository and the `type` of the pull request's author and of the event's sender, never a named account. The skip reaches the genuine version pull request only once its author is a bot whose push retriggers CI — under `secrets.GITHUB_TOKEN` that pull request raises no workflow run at all, so there is nothing to skip, and the comment above the step now says so rather than warning about a hole that is not one.

`oakum ci version-pr` says who the token opened the pull request as, on stderr — stdout stays the one URL a caller captures. A run under a personal access token opens it as a person, which the scaffolded skip does not excuse, so every check runs on the version pull request and the only other symptom is a longer bill. The identity is reported where it was measured rather than left to be inferred from a workflow that did or did not fire. It is reported, not read as a verdict: a person settles the question, because that term alone defeats the skip, while a bot does not, since the skip also tests the sender of the event the push raises and no run can see that from here. A response that omits the author, or omits its type, says so instead of defaulting into a verdict.

The workflow `init` and `migrate` print surfaces a `pr-status` run that could not post its report. That step carries `continue-on-error`, so a GitHub outage does not fail a contributor's check; the same setting also let a report that never posted pass for one that did, and left a green check over a log nobody opens. A step now follows it that, when the step failed, emits a warning into the run summary and names the check above as what still decides. It runs whether or not the check itself passed, since a failed check is exactly when the report matters. A post that fell back to the job summary, the designed path for a fork with no token that can comment, is not a failure and does not warn. oakum's own workflow gains the same step.

### Fixed

`oakum check` prints its refusals as blocks, the deciding line first. Each refusal's summary comes first with its detail indented beneath it, and every refusal that did not decide the exit code follows as `also …` in the same shape, so a reader meets the verdict before what is subordinate to it, and evidence sits under the line it supports; two looks that fail identically say it once, keeping what each found. Before, each look printed its detail as it ran and its summary at the end, so the management guidance could sit five lines from its summary with three unrelated lines between, and `also` lines printed before the line they were also-to. `tag-drift` prints the same block for the same state, and with a stale install pin beside real drift it now exits 1 for the drift and names the pin as `also`, as `check` does.

Among refusals of one class, the order `check` announces decides which one carries the exit code, and the install pin is its own look after the tags. With git wholly unusable, the first line a reader meets says git could not run, not `install pin is 9.9.9`. Before, the pin was verified inside the tag look and before git was touched, so a stale pin decided for a repository whose git did not work. A base ref git cannot resolve is quoted on the scope line by its first line only; the coverage look still carries the whole failure.

No command loses its output to a panic when the reader has gone away. `println!` and `eprintln!` abort on a refused write, so `oakum version | head -1` exited 101 — neither ok, unverified, nor error under ADR-0034 — with its files already written and no account of them, and every other command shared the hazard. 0.3.0 said both channels went through a write that reports failure rather than panicking; that was true of `check` alone.

Every command now prints through writers that do not abort, and they differ by what the line is. A report — a `check:` scope line, a `pending:` plan, a migration step — survives a refusal in silence, because a reader who went away chose not to read. A result is the command's return value: the path `add` wrote, the URL `release` or `ci version-pr` opened, the plan `status` prints and the JSON `status --json` and `plan-intent` produce, the body `generate --dry-run` composes, the listings `reachable-tags` and `detect-release-tools` are, the summary `version` or `upgrade` gives of what it changed, the `created` records and the workflow `init` and `migrate` hand over, and the plan `ci pr-status` falls back to stdout when it has neither a token nor a job summary. A result nobody received is a run that did not answer. It exits 2, `unverified` under ADR-0034: the work landed and the answer did not, the same shape as a `migrate` that applied every file and could not verify them. Stderr says what already happened, so a caller that captured an empty stdout under `set -o pipefail` is told rather than left to notice. A descriptor the caller closed outright (`>&-`) is not a reader who went away: the standard library reports that write as delivered, and the run exits 0.

`init` and `migrate` finish every write before reporting a refused record, so a reader that went away does not leave `.changeset` half-written, and the verdict names each line that never arrived, even when a plan-comparison finding outranks it for the exit code; a write that fails after such a refusal, a gate look that fails beside it, or a comparison that could not run is named in the same verdict. An interactive prompt propagates the refusal because a question that cannot be shown cannot be answered. A `release` stopped by such a refusal keeps that class through its partial-failure report rather than reading as an error, and that report lists a tag whose GitHub release exists as `released` and not as remaining. A test fails the build naming any command module that reaches for the macros again.

`oakum ci pr-status` identifies the version pull request by the same four facts the scaffolded workflow tests — head branch, head repository, and the type of both the author and the sender — where it read the branch name alone. A fork or a collaborator naming a branch `oakum/version-packages` was treated as the version pull request, which suppressed the coverage comment on their own change. The cost of the other mistake is a redundant comment on the real version pull request, so an event that cannot be read counts as not the version pull request.

`oakum ci pr-status` reads `.changeset/_config.toml` once per run. It read it twice, once to choose the channel and once more inside the state builder to compose the plan, so a config edited between the two reads could choose a channel with one config and build the plan with another. `status`, `ci pr-status`, and `version` share one plan pipeline; `version` carried its own copy of it.

A release assembled from a bump file that declares more than one section renders each under its own heading. A note's first line was the only one read for a section name, so a file carrying `### Added` and `### Changed` was filed under the first and printed the second inside that block; 0.3.0's own changelog repeats `### Changed` and `### Fixed` for that reason. A known heading now starts a section wherever it appears, at up to three columns of indentation — the rule CommonMark applies and the one oakum's fence reader already used — while a fourth column is code, an unknown heading such as `### Notes` stays body text, and a heading inside a fenced block stays content. A heading with nothing but whitespace under it renders no section rather than a heading over two spaces. A template iterating `changes` or `notes` sees the same correction: a bump file's second section is its own entry, sharing that file's commit, pull request and author, rather than a stray heading buried inside the first entry's body. The rows a template rendered before were the bug, not a contract it can keep. MD024 stays disabled repo-wide, because specs and decision records repeat headings by design; the rendered changelog asserts the rule itself instead.

A `version` run that fails partway names every file it left changed, as a list. Rollback appended `; restoring X also failed (...)` to the cause once per file, which buried the last entry of a chain, and the one run where the tree is left half-written was the one that said least about it. The failure now prints the cause, a count, and one path per line. Two states that were silent are now named as files left changed: a staging file the run created and could not remove, and a file the run created and could not remove after the write itself failed. A directory the sweep could not read is named too, on its own line and under its own heading, because it is no evidence of a changed file — the fault that strands a file is the kind that also blocks the listing, so silence would hide a leak exactly when there is one, while counting it as damage sends a reader hunting for a half-written tree that may be intact. A staging file is attributed to this run by a delimited process id rather than a substring match, so a concurrent run's file is not named as this failure's; the wording holds either way. An empty list is documented for what the code checks — every restore reported success and every swept directory could be read — and no longer claims a byte-identical tree, which rollback does not verify because it writes the planned original back without re-reading it.

`version` writes a file it planned to create with an empty body, where the unchanged-text skip dropped the write and reported success over a file that never appeared. No caller produces one today.

`version` no longer loses its summary to a panic when the reader has gone away. `println!` aborts on a refused write, so `oakum version | head -1` exited 101 with the manifests, changelogs and bump files already written and no account of any of it — on the one command that performs the irreversible part of a release. The summary now goes through the same write that `check` was given in 0.3.0, which reports a refusal rather than panicking. Other commands still print directly, which is tracked separately.

## 0.3.0 (2026-09-12)

### Added

`migrate` derives `tag-format` from the tags a repository already carries, so a cutover from a tool that tags `name@version` no longer meets oakum's `name/v1.0.0` default at the first release. Derivation is structural rather than a list: a shape is written only when one template explains every tag, and only when oakum's own tag reader can read that shape back. Tags that disagree, or that no split explains, write nothing and are named among the remaining steps, because refusing beats cutting a tag the repository does not use; the shapes this repository could adopt are listed beside the ask, since which one is right depends on the tags it could not reconcile. That list drops any shape the workspace cannot use — above one tag-managed package the bare `v{{ version }}` is absent, because a release reads such a tag as leftover ambiguity, and the step that refuses a bare shape must not then offer it. A repository whose tags cannot be read is told so rather than treated as having none.

`migrate` also names the install pin among its remaining steps when the repository has none, quoting the version it just wrote to `tool-version` and the install command for the ecosystem it detected — the same one the workflow it prints below uses, rather than both ecosystems' commands regardless. Without a pin every later oakum command refuses, and a reader who installed globally would otherwise meet that refusal with the migration already applied.

A migration guide, at [docs/guide/migrating.md](https://github.com/oakoss/oakum/blob/main/docs/guide/migrating.md). It covers which source settings carry and which do not — and the three different reasons a setting does not carry, since "no counterpart, nothing lost" and "no counterpart, but your release commits change author" want different responses from a reader. It puts the remaining steps in dependency order rather than in the order they print, because pinning the binary before pasting the workflow is the difference between a clean cutover and meeting a refusal with the migration already applied.

It also names the one part of a cutover that cannot be ported: a pipeline built on a plan/act split, where one job computes a mode and downstream jobs run guarded by `--expect-mode`, has no equivalent here. oakum has no plan step — `ci version-pr` and `release` each derive their own precondition from repository state when they run — so there is no window between deciding and acting to guard. That is a different safety argument rather than a weaker one, but it means the workflow is rewritten, not translated.

The guide leads with the acceptance test, which is **`oakum status` names every package you expect to release** — not "`check --strict` exits 0". One real cutover was given the second and satisfied it immediately with a config that managed nothing. oakum has since closed the specific hole that cutover fell into: a config whose only packages are private now exits 2 and names the fix. One shape still passes deliberately — an `include`/`exclude` that selects nothing exits 0, because emptying a selection is a decision the config states and a gate must not refuse one. The argument is narrower for that, and it still holds: a plan is a positive statement about what will happen, a gate exiting 0 is the absence of a complaint, and reading the plan needs no guard to have been written in advance for the particular way your config is wrong.

`oakum migrate` now names what the repository can retire, instead of leaving it to be found in the schema. `extra-files` declares a JSON file that carries a version — a plugin manifest, a marketplace entry — and `oakum version` writes it in the same pass as the manifest and under the same rollback, which retires a sync script, its drift job and its tests. v1 writes JSON only, so a chart or a README badge is refused at config parse rather than written. The reporter who found this called it the strongest argument for the migration, and found it by noticing a phrase in `oakum version --help` and then reading `_schema.json`.

### Changed

The GitHub Actions guide says why the printed workflow carries no `concurrency:` block, and does not tell you to omit one. Whether a group is load-bearing depends on whether the pipeline carries a decision between jobs: one that does needs protecting from a cancellation window, and one that re-derives its preconditions per command does not. This repository's own workflow carries a group and the printed one does not, and both are correct for that reason. The earlier guidance would have generalised another tool's failure without checking whether the mechanism carries over.

`status` reports a changed package the config keeps but cannot version — a private package where `private-packages.version` is not set, so no bump file could ever cover it. It appears in the rendered summary and as an `unmanaged` array in `--json`, and it does not change the exit code. `check` stays silent on that state on purpose: `status` reports, `check` decides, and there is nothing here to decide.

`status --json` reports coverage for real. It emitted `uncovered: []` for every repository, whatever had changed, because the command never ran the coverage look — only `check` and `ci pr-status` did. `schema_version` is deliberately unchanged: the new fields are additive and an old parser sees the shape it always saw, but a reader that treated an empty `uncovered` as a clean result should now read `coverage`, which says what happened to the look — `ran`, `failed`, or `not-asked`. The third is not a hedge: a report rendered from a plan already in hand, such as the Version Packages body, never asks the question, and saying the look failed there would blame git for something nobody attempted. Where git cannot diff the tree, `status` says so in the rendered summary as well as the JSON, since stderr does not reach a step summary or a pull-request body.

`status` distinguishes a repository with nothing pending from one whose config manages no package on either axis — every selected package private, with the opt-in unset. Both printed `No packages planned.` and exited 0; the second now says so, and carries `manages_nothing` in its JSON. A selection that `include`/`exclude` empties is not covered by this and stays silent, in `status` as in `check`, because an empty selection is a decision someone wrote down. `ci pr-status` reports the same facts, and no longer stays silent on such a repository — it planned nothing and covered nothing, so the early return swallowed the one thing worth saying.

### Changed

`check` refuses when no selected package can produce work on either the version or the tag axis, where it exited 0 in silence. That state plans nothing and releases nothing while every gate reports green, and it is what a migration produces when the private-packages opt-in is lost. The refusal names both keys. A selection left empty by `include`/`exclude` stays silent, because that is a decision someone wrote down, while an absent `private-packages` key is the absence of one. `release` does not ask, so a release with nothing to do still says so in its own words.

`init` says the same thing where it writes such a config, rather than leaving it to the next command: an all-private workspace still gets its files and a zero exit, with the guidance on stderr.

`check` refuses a bump file that names a package it cannot version, matching what `status` and `version` already did. It asked a narrower question than the pipeline — it let an `include`/`exclude` exclusion through — so a repository could pass a green `check` and then have its version PR fail on the same file. If your `check` is green today on a bump file naming an excluded package, it will now fail, and so would the release that followed it. The refusal names every offending package and prints before returning, so a failure in an earlier look, such as a missing install pin, no longer erases it.

The coverage look refuses a shallow clone instead of reporting a clean result. At depth 1 the default base resolves to the checked-out commit itself, so the diff came back empty and every changed package looked covered. `actions/checkout` clones that way unless told otherwise, which made this the common CI shape rather than an edge case. `check` already refused such a clone through its tag look; `ci pr-status` did not, and now does, naming `fetch-depth: 0`. `status` reports it rather than refusing, because `status` is not a gate.

`check` stays silent on a changed package the config keeps but cannot version — an unpublishable package where `private-packages.version` is not set. That is a choice someone made, not a fault, and gating on it would turn every private-package change red until they wrote config; [ADR-0027](https://github.com/oakoss/oakum/blob/main/docs/decisions/0027-private-packages-version-opt-in.md) records that silence as something a changesets migratee keeps without a config change. `status` reports it instead — see the Added note.

`migrate` no longer calls an empty plan comparison a match. With nothing pending on either side it printed `0 package(s) planned by bumpy and by oakum; match`, which reads as verification of a transform that nothing exercised. That is the common case rather than the rare one, since a repository is usually migrated right after a release.

`oakum check` says what it covers, on every run. It exited 0 with no output at all, so a check that inspected a two-package workspace and a check that inspected nothing were the same observation — and a config selecting no package read as a clean repository. Every run now opens with two lines on **stdout**: how many of the workspace's packages the selection keeps, the ref the diff is taken from, the looks this run asks for, and — separately — the looks it does not, because a look nobody asked for must not read as a look that passed. The lines state scope and intent, never a verdict: they print before the first look so that a run which refuses describes itself too, and what became of those looks is the exit code's to say — nothing on stderr and exit 0 means every announced look finished and passed. **Breaking for anything that asserted `check` writes nothing to stdout**; the refusals themselves are unchanged and still land on stderr. Every look's refusal now reaches stderr, too: the looks are run together and then raised in order, so the second and third used to be discarded — a `--remote` run against a repository with no remotes lost that finding entirely whenever an earlier look refused first. And the base ref the report names is confirmed before it is quoted, so an explicit `--from` naming a ref git does not have is reported as that rather than announced and then failed on.

When a run refuses on more than one look, the refusal that sets the exit code is the one oakum measured, not the one written first. `check` runs its looks together and then raises one; it raised whichever came first in the source, so an unrelated leftover staging file turned a measured tag drift from `error` (exit 1) into `unverified` (exit 2) and erased the `error:` line from stderr — ADR-0034's split run backwards. A finding now outranks a look that did not happen ([ADR-0035](https://github.com/oakoss/oakum/blob/main/docs/decisions/0035-a-finding-outranks-an-unverified-look.md)), and every other refusal is still reported, prefixed `also`, so a reader can see which line the exit code came from. **Breaking for anything branching on `1` versus `2`**: a repository with both a finding and an unverified look now reports the finding. A base ref git does not have is `unverified`, not an error — a shallow CI checkout passing `--from` is the shape that hits it.

Neither a report nor a refusal that cannot be written replaces the outcome with a panic. `eprintln!` aborts when the write is refused, so a run whose stderr reader had gone away exited 101 and printed nothing at all, in place of the exit code ADR-0034 defines. Both channels now go through a write that reports failure rather than panicking — `oakum check | head -1` is an ordinary invocation, and the report this round added made it an exit-101 one.

An unverified outcome prints one outcome token on stderr, not two. Every failure was prefixed `error: `, and an unverified message already begins `unverified: `, so stderr read `error: unverified: …` — two words saying different things about one result. Both channels now read one classification of the variant, so the prose and the numeric channel (ADR-0034: `2` for unverified) cannot disagree — two exhaustive matches would have let a variant be filed one way for the shell and another for stderr. **Breaking for anything matching `error:` on an unverified failure**; it now matches `unverified:`.

### Fixed

An unknown configuration key is named, fully qualified as TOML resolved it. A scalar written below a table header is scoped into that table, so `commit-message` typed at what looks like the top level is read as `private-packages.commit-message` — and the error gave a line number with nothing on that line to look for. The name comes from a span-preserving parse rather than from reading the source text, so a header carrying a trailing comment is still that key's table, a key inside an inline table is named at its own depth, a bracketed line inside a string value is not mistaken for a header, and a header is named the way TOML resolved it — spacing dropped, but a name that genuinely needs quotes keeping them, so the path is one the document holds. A key the parse cannot place keeps the message it always had, and a document that omits a required key is reported as that rather than as `invalid TOML syntax`, which sent readers hunting a typo in TOML that parses perfectly. Values are still never echoed, and neither is the source line.

A template that reads an undefined variable names it, and names the variables in scope. `tag-format = "{{ name }}"` failed with `undefined value (in tag-format:1)`, which named neither the offending variable nor the correct one — `package`, findable only by reading oakum's source. Both halves are derived: the unsupplied names are the template's own undeclared variables minus what the context supplies and minus the renderer's globals, and the scope is the context's own keys. It is stated as a set — "this template reads `name`, which the context does not supply" — because that is what the analysis knows: it reports every name the template reads anywhere and cannot say which branch ran, so calling one of them the cause of this failure would claim more than was established. A nested read is resolved against the context rather than matched against its top-level keys, so `repo.url` is not accused of being missing and `repo.nope` still names itself. A context that is not a map says so rather than reporting no variables at all. This covers every rendered surface, not just `tag-format`. The four template keys in `_config.toml`'s schema now name the variables each surface receives, and a test ties each list to the context that surface actually renders with.

A git operation that failed for a non-ssh reason no longer reports an ssh configuration problem. oakum resolves the ssh transport once and puts it on every child, including local ones; when that probe failed, every operation was reported as needing `an ssh configuration oakum could not read`, with the real cause in parentheses and a remedy measured to move the failure rather than fix it — including when git was not installed. Four outcomes are now kept apart: a repository git will not open is reported as itself; an ssh configuration git would not give up keeps the skip-the-probe remedy; an ssh *variable* oakum cannot read is told to repair or unset that variable, rather than being answered with advice to set it; and a probe that never reached git at all claims no cause, because offering one would be a diagnosis nobody made. A child that died on a signal counts as the last of those: it establishes nothing about ssh or about the repository. The second probe is also asked only when the first one ran and refused, which halves the worst-case wait on a git that hangs.

`oakum status --help` says which render a bare `status` produces. It described the command as printing `JSON or a named render`, which reads as JSON being the default; it is the `summary` render, and the reporter ran both commands to find out.

`oakum migrate` names `gitUser` as a step rather than a forgettable dropped key. It decided who authored every release commit and tag; oakum has no counterpart, so a cutover reassigned authorship silently. Both the step and the printed workflow now say what that identity actually governs, because the two halves differ: annotated tags take the `git config user.name` / `user.email` the release job sets, while the version commit is written through the GitHub API and carries the token's own account, which no git config can change. A reader swapping in a GitHub App token — which a bot push needs to retrigger CI — changes the commit author whatever they configure.

A failed bump-file gate look states one fact. The printed step and the `unverified` refusal were two separately-authored sentences about one outcome, each free to drift from the other; they still read differently, because one is a bullet and one sets the exit code, but the fact they state now comes from one place. Which outcome refuses is a property of the look rather than a `match` repeated at each site.

An outcome oakum could not verify now exits `2`. Every failure exited `1`, which put "this repository failed the check" and "the check could not be run" behind the same number — the collapse the three-outcome rule exists to prevent, surviving in the one channel a caller reads without parsing prose. The three outcomes are now `0` ok, `2` unverified, `1` error, decided in one place and applied by every command that can report one. Every exit stays non-zero, so `set -e`, `if ! oakum check`, and a GitHub Actions step all behave as before; a script comparing the code against `1` exactly does not. See [ADR-0034](https://github.com/oakoss/oakum/blob/main/docs/decisions/0034-exit-two-for-unverified.md).

`migrate` is where this was costing the most. A cutover that wrote every file correctly and merely could not run the source tool to compare against reported `error: unverified: migrated files were kept` and exited `1` — indistinguishable from a migration that failed, on the path the install docs produce.

### Fixed

`migrate` carries a source tool's `privatePackages` into oakum's `private-packages`, where it dropped it. A repository whose packages are all private migrated to a config that managed nothing, so `check` exited 0, `status` planned nothing, and a release would have done nothing while reporting success. Changesets' bare-boolean form is read the way changesets reads it, as both axes. Both source files are read when present and their axes are unioned, so a repository migrating from one tool while a readable config from the other is still on disk carries both; the report names what each file contributed and the one line the write produces. A bumpy source also gets the "not carried over" report the changesets path already had. A source config oakum cannot open, read, or parse, or one whose axis is not a boolean, is reported and skipped rather than stopping the migration: both tools accept JSON their own loaders tolerate and `serde_json` does not, so a leftover config from an abandoned experiment no longer aborts an unrelated migration. A dangling symlink at either path is named as one rather than read as the file being absent.

`migrate` looks for the source tool in `node_modules/.bin` before giving up on it. `npm i -g` and Homebrew put `oakum` on `PATH` and a devDependency's binaries nowhere near it, so the install the docs recommend left the parity check unrunnable — on the one command whose whole job is comparing against that tool. The comparison then ran oakum against oakum, which cannot detect a mapping error, and said `match` about it. A source tool that really is absent now says where oakum looked, because installing globally and installing locally fix different halves of that. A source tool that ran and failed is no longer mistaken for one that answered: a crash whose output happens to parse is not an empty plan, a child the kernel killed is reported as such rather than as `exited -1`, and a difference measured against a plan read under a tool's exit-1 convention is unverified rather than proof the transform changed anything.

A tag that states no version — `v1`, `latest`, `nightly`, a date stamp — no longer cancels the whole tag-format derivation. `release` already classifies such a tag as someone else's and skips it, so one `v1` (the GitHub Actions convention) turned the derivation off on exactly the histories it was written for, and the two commands disagreed about the same tag. A history of nothing but moving tags is still reported, naming them: it has tags, and calling that "no tags" would say never released about a repository nobody managed to read.

`migrate` says which `versioning` mode it wrote and what settled it. `semver` is the non-default, and for a repository whose packages are all below 1.0.0 it is the difference between the next release being `0.18.0` and `1.0.0` — written silently until now. knope and release-plz imply `zero-major` instead; release-plz's own configuration documentation states the rule, and it had been grouped with the tools that take `0.1.3` to `1.0.0`.

A bump file copied out of the old tool's directory is described as a copy rather than a rewrite, and every original left behind is named among the remaining steps. oakum does not own that directory and will not delete from it, but the old tool goes on counting those files: measured in a clone, after `migrate` and `version` released a package 0.17.0 to 0.18.0, the old tool still showed three pending and would have released it again. A repository whose workflow still runs the old tool on every push to `main` gets that second release on the merge commit.

`migrate` names what in a repository refers to the old tool's bump-file directory, so a commit hook or CI step pointed at it can be repointed before it rejects the bump files oakum writes — which is what happened in the first repository to adopt oakum. oakum cannot tell a gate from a mention in prose, so the step asks the reader to look rather than asserting each match is a gate, and it says what it did not search: the look reads git's index outside `.changeset/`, so an untracked file, an unstaged edit, a submodule and `.git/hooks/` are all uncovered. A look that fails says so and exits unverified rather than passing for no gate. Only a bumpy cutover has an old directory to repoint anything at; changesets and knope already keep bump files in `.changeset/`, which oakum adopts in place.

The plan `migrate` prints is sorted. It came out in filesystem order, so the same repository could show a reader a differently ordered plan on a different machine.

A difference the parity check found outranks a look that could not happen. The first is a finding and the second is missing evidence, so a migration that proved the release plan changed reports that, at exit 1, even when the gate look also failed.

`oakum version` says what it wrote. The command that performs the irreversible part of a release — manifests, lockfile rows, changelogs, declared `extra-files`, and the bump files it consumes — exited 0 having said nothing at all, so a run that rewrote five files was indistinguishable from one that did nothing. It now names each package with its old and new version, says which package triggered a cascade, lists every file whose bytes changed, and names every bump file consumed. Printed after the writes land, so it reports rather than promises. `ci version-pr` plans the same writes through a different path and its output is unchanged.

The `.changeset/README.md` oakum writes no longer documents a bump-file form the parser refuses. It said oakum reads a quoted bare package name; `status`, `check` and `version` all refuse one, naming the file — `docs/specs/bump-files.md` has always listed quoted keys as not permitted. Since `init` and `migrate` write that README into the repository, the tool was teaching a rule it then rejected people for following. The corrected text also records that `migrate` rewrites the quoted form `@changesets/cli` writes, so a cutover needs no hand-editing.

`status` reports a config whose `include`/`exclude` leave no package selected. Such a config can never release anything, and both verbs said only `No packages planned.` — the same sentence a quiet repository prints. `check` still stays silent, because emptying a selection is a decision the config states and a gate must not refuse one; `status` is not a gate, so it says what the reader is looking at, and says that `check` will not refuse it. `status --json` carries `selection_empty` beside the existing `manages_nothing`; the two are exclusive, and a document asserting both, or asserting either beside a planned release, reads as neither.

`ReleaseState::manages_nothing` is no longer `const`, and the new `selection_empty` accessor is not `const` either: both read `packages.is_empty()`, which is not a const operation. A caller using either in a const context breaks; nothing in oakum does, and the library's `pub` surface is the seam between it and the binary rather than a curated API.

`migrate` carries `versionCommitMessage` into `commit-message`, an exact equivalent it previously left for the reader to restore by hand — and says so before writing it, beside the other settings it carries. A message equal to what oakum writes anyway is not written as a config line restating a default, and the run says that rather than reporting a loss that did not happen. A message oakum cannot carry is named with the reason: `commit-message` is rendered as a template, so a literal containing `{{ … }}` would fail the version PR or quietly become a different message, and a control character has no place in a commit headline; a newline ends the config's string form outright. `changelog` is named as a decision the reader owes rather than translated, because it means different things in each source tool and neither is oakum's `template`.
