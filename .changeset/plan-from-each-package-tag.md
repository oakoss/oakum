---
oakum: major
---

With conventional commits and change files off, the plan (`status`, `version`, `check`, `ci pr-status`, `ci version-pr`) now reads each package's commits since its own highest reachable tag, instead of `merge-base(origin/main, HEAD)..HEAD`. On the default branch that range was empty, so a commits-only repository planned nothing there unless every run passed `--from`; `version` now releases on `main`. A package never tagged reads all of its history. A package `version` released and no tag records yet (its manifest is above its tag and its changelog has the section) reads no commits until `oakum release` tags it, so the version pull request job running beside `release` does not plan the same release twice, wherever the release was cut; `check --strict` still reads the branch's commits for it, so a branch's own fix covers its change. `status` lists it under "Released, awaiting its tag", and `status --json` and the templates as `awaiting_tag`. A package oakum does not tag keeps the merge-base range. A shallow clone, a `--no-tags` remote, tags oakum cannot attribute, or one version tagged on two commits now make these commands unverified (exit 2) in commits-only mode, where the plan read no tags before. With a tag to read from, `status` no longer needs `git merge-base` for the plan, so a merge-base it cannot get now leaves only its coverage look unchecked (exit 0, "Coverage was not checked") rather than failing the run. `--from` still reads one range for every package, `generate` keeps the merge-base range, and `check --strict` still asks what changed since the merge-base, now against intent pending since each tag.
