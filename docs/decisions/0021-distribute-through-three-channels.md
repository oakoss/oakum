# Distribute through crates.io, Homebrew, and npm, with npm as a fetcher

- Status: accepted
- Date: 2026-08-18
- Deciders: Jace Babin

## Context and Problem Statement

oakum is a Rust binary that has to run in repositories whose contributors may never have installed Rust. A JavaScript monorepo pinning a release tool expects to pin it the way it pins everything else. Which channels does it ship through, and how does a Rust binary reach a `package.json`?

## Decision Drivers

- Every repository surveyed declares `packageManager: pnpm` ([ADR-0012](0012-scope-v0-to-version-math-and-the-github-layer.md)), so npm is where the pin naturally lives
- [ADR-0007](0007-pin-the-tool-version-in-config.md) requires a workflow to invoke an exact version, which only works if the channel supports pinning
- The distribution machinery is already owned: linesmith ships through cargo-dist to `oakoss/homebrew-tap` (verified 2026-08-18)
- [ADR-0018](0018-own-the-plan-engine.md) rules out a Node runtime dependency, which constrains what an npm package may contain

## Considered Options

- crates.io only, and let non-Rust repositories install Rust
- crates.io plus Homebrew, matching linesmith
- crates.io, Homebrew, and npm

## Decision Outcome

Chosen option: **all three**, generated by cargo-dist rather than hand-built.

linesmith's `dist-workspace.toml` already carries `installers = ["shell", "powershell", "homebrew"]`, `publish-jobs = ["homebrew"]`, and `tap = "oakoss/homebrew-tap"`. oakum adds `npm` to both lists. The tap exists and is in use, so Homebrew costs a line.

**The npm package is a fetcher, not a bundle.** It carries an install script that downloads the platform binary rather than vendoring binaries for every target into the tarball, so the package stays small and one build feeds every channel.

It is not JavaScript-free, and pretending otherwise would hide the risk. cargo-dist generates a `run-<bin>.js` shim that the package's `bin` field points at, so every invocation starts Node and spawns the binary from there, alongside 10 KB of download, extraction, and proxy logic in a 13.8 KB package. **That shim is the surface to watch:** nothing that computes a version, resolves a range, or reads a manifest may ever move into it. See [cargo-dist's npm installer](../research/cargo-dist-npm-installer.md).

### Consequences

- Good, because a JavaScript repository pins oakum in `devDependencies` and its workflow resolves the pinned version the way bumpy's does, with `jq` and nothing else
- Good, because one cargo-dist build produces every channel, so the versions cannot diverge
- Bad, because the npm channel needs two origins at install time — the registry for the package, then the artifact host for the binary. An environment with an internal npm mirror but no route to the artifact host installs and then fails in `postinstall`. No channel here works offline: Homebrew fetches from the tap and the release, and crates.io needs the registry and the dependency tree unless everything is vendored
- Bad, because three channels are three ways for a release to half-succeed. [ADR-0011](0011-stop-at-the-tag.md) applies: stop and report precisely, never roll back
- Neutral, because it makes oakum's own release a multi-target publish before it has ever released anything — the bootstrap in [ADR-0007](0007-pin-the-tool-version-in-config.md)
